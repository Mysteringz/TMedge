# Location configuration storage

This guide covers durable location drafts, published revisions, source assets and public GLB delivery. Task 2.1 supplies persistence; Task 2.2 assembles and activates a complete live runtime generation on publish; Task 2.3 adds the authenticated Algo location API and split edge/web asset flow. The editor is delivered by later tasks.

The current HTTP contract, including console routes, edge GLB ingress, authentication, revision checks, payload limits and student model reads, is documented in [location-management.openapi.yaml](location-management.openapi.yaml).

## Storage ownership

- `SITE_CONFIG` is the read-only legacy seed. It supplies existing floors and their geometry.
- In file mode, `NODES_CONFIG` is the live registry. The edge validates both seed files before upgrading a legacy `{ "nodes": [...] }` document to schema version 2. The upgrade uses a same-directory temporary file, file flush and atomic rename. The v2 file stores node registrations, a global registry revision, and published location history.
- File drafts and source assets live under the persistent edge `DATA_DIR`, outside release directories. Draft files are scoped by a one-way creator hash. Asset IDs and filenames are generated by the server; PNG/JPEG or GLB bytes and metadata are immutable and creator-scoped.
- In PostgreSQL mode, the explicit migration creates the global registry revision, owner-scoped drafts, immutable published history, active revision pointers and asset metadata. Asset bytes remain under edge `DATA_DIR`.
- The Algo location API is available to named Admin and Operator accounts through the existing signed console session. A dedicated `locations.manage` capability does not extend to Engineer or Viewer accounts. Drafts and asset previews are private to their creator; the API derives actor identity from the session and does not accept visibility or asset-owner fields.
- Location documents are limited to 1 MiB and polygons to 256 vertices. Uploaded floor plans are limited to 20 MiB and GLBs to 128 MiB by default. PostgreSQL asset metadata and published revision rows reject updates and deletes; a metadata record with missing bytes fails closed.
- Legacy `console` visibility is copied into revision-zero documents and remains server-managed through edits. New documents default to `public`; RGB sensors can only be assigned to console-only locations in both file and PostgreSQL modes.
- A public revision with an uploaded GLB is committed only after every configured `WEB_PUSH_URLS` target accepts the edge-authenticated immutable transfer and acknowledges its asset ID and SHA-256. `WEB_PUSH_TOKEN` authenticates that transfer in shared-token mode. If `WEB_EDGE_KEYS_FILE` is enabled, v1 explicit floor ownership takes precedence; an unlisted generated floor may be written only by the edge whose ID matches `location_<edgeId>_<UUID>`. Console-only uploads remain on the edge, and revision-zero static models keep their existing fallback without a GLB transfer.
- The web tier stores transferred GLBs under `DATA_DIR/published-models` (or beside `USERS_FILE` when `DATA_DIR` is unset), outside the release and static-public trees. The student model route requires a student session and an exact reference from the current winning public snapshot. Bytes left by failed or superseded publications are not readable without that winning snapshot reference.

The edge process holds `NODES_CONFIG.writer.lock` while it owns the file registry. Run one edge writer for that registry. If the lock remains after a crash, confirm the service is stopped before inspecting or removing the stale lock; the application intentionally fails closed while another owner may still be active.

## Deployment

Keep `SITE_CONFIG`, `NODES_CONFIG`, PostgreSQL data, edge `DATA_DIR`, and web `DATA_DIR` outside the versioned release tree. Production releases already use `/var/lib/tmedge` for persistent data; keep the edge and web persistent data directories there on their respective tiers and point `NODES_CONFIG` to a persistent file. Do not restore a release copy over the active registry or place model bytes beneath `public-web`.

For PostgreSQL mode, create separate migration and runtime roles. Apply reviewed schema changes explicitly with `npm run db:migrate` using the migration credentials before starting the new edge release. The runtime role needs schema usage and table/sequence data privileges, but no schema creation privilege. Automatic TypeORM migrations and schema synchronization remain disabled. The edge refuses to start if the required migration is absent or storage validation fails.

The legacy `db:registry:import` command remains the explicit, idempotent path for importing node registrations into PostgreSQL. Existing registrations, placements and table ownership are preserved; location bootstrap adds revision-zero documents only when a seed floor has no active history. `--apply` is offline maintenance: stop the edge before applying and restart it afterward so the process loads the imported registry. The command cannot verify that the edge is stopped; its advisory lock coordinates database writers but does not activate a running process's in-memory registry.

## Backup and restore

Back up and restore these items as one recovery set:

1. The active `SITE_CONFIG` and `NODES_CONFIG` files in file mode, or a PostgreSQL dump in database mode.
2. The complete edge `DATA_DIR`, including private drafts and immutable source asset bytes.
3. The web tier's complete `DATA_DIR/published-models` directory, including durable student-tier GLB bytes. Edge and web bytes share opaque asset IDs/digests; restore each directory only to its corresponding tier.
4. The deployment environment/configuration needed to point both tiers back to those same persistent paths and preserve `WEB_PUSH_URLS`, publisher credentials, and the selected authentication mode.

For a consistent backup, stop or quiesce the edge writer while capturing the registry/database and edge `DATA_DIR`. Keep the PostgreSQL dump and edge `DATA_DIR` from the same backup point: database asset metadata and location references are not useful without the matching bytes. Include the web model directory in the recovery set; a web restart does not restore snapshots, so student model reads remain denied until the edge pushes the current snapshot again. Restore each data directory with restrictive filesystem permissions before starting its service.

`npm run db:revert` reverses the last applied migration and drops its location tables, including drafts and published history. Take and verify a backup before using it; it is a schema rollback, not a routine code rollback. File-mode registry history is retained in `NODES_CONFIG` and should be backed up before any manual edit.
